# 데이터·실험 공통 기준

여러 팀원과 AI가 같은 데이터를 다른 뜻으로 처리하지 않도록 사용하는 합의 문서다. 아래는 [프로젝트 제안서](../Team1_proposal.pdf)의 계획과 미정 항목을 구분한 현황이다. 실제 데이터·코드로 확정되지 않은 설정을 구현 완료로 취급하지 않는다.

## 1. 결정 현황

| 항목 | 제안서 기준 계획·미정 항목 | 확정할 때 남길 내용 |
| --- | --- | --- |
| 주제·문제 유형 | 사진 기반 분리배출 안내 PoC, 품목 다중 분류 | 예측 시점과 분류/회귀 정의 |
| 데이터셋·버전 | AI Hub 재활용품 분류 및 선별 데이터·Kaggle Garbage Classification·TrashNet 후보. 최종 선정 미정 | 출처·다운로드 날짜·파일 해시·사용 조건 |

| 타깃 | 단일 물건 사진의 품목. 세부 클래스는 데이터 확보 후 확정 | 컬럼·라벨 의미·단위·생성 시점 |
| 상태 판별 범위 | 오염·라벨 등 물건의 상태는 판별하지 않음 | 품목 분류와 상태 판별을 구분하고 범위 변경 시 재합의 |
| 배출 안내 전제 | ‘내용물을 비우고 헹군 상태’를 전제로 안내 문구에 함께 표시할 계획 | 공식 기준 출처·규칙표 버전·품목별 안내 문구와 적용 조건 |

| 분할 | 층화 70:15:15 및 동일 물체 그룹 분리 계획. 방법·seed·ID는 미정 | 방법·비율·그룹/시간 제약·seed·ID 보존 방식 |
| 전처리 | 손상·중복 정제, 수치 피처 스케일링, CNN 이미지 크기 통일·정규화 계획 | train에서 학습할 처리, 적용 순서, 출력 스키마 |
| 평가 지표 | Macro-F1(주), 품목 정확도, 배출 방법 정확도, 전용 수거 품목 재현율 계획 | 이름·집계·방향·양성 클래스·임계값·단위 |
| 모델 선택 기준 | 공통 validation에서 Macro-F1 중심 비교 계획. 동점 처리·확신 기준값 미정 | validation 또는 CV 기준과 동점 처리 |
| 환경·의존성 | Python 3, scikit-learn·OpenCV·scikit-image, 선택 과제 PyTorch+Colab 계획. 버전 미정 | 확인한 Python·패키지 버전·CPU/GPU |

피처는 이름뿐 아니라 순서와 의미도 공유한다. 인코딩된 클래스·확률 열의 순서, 목표값의 변환과 역변환을 명시하여 학습과 평가가 같은 뜻을 쓰도록 한다.

배출 방법 단위의 평가는 위 전제와 규칙표를 기준으로 정의한다. 품목 분류나 규칙표 연결이 맞았다는 결과를, 물건의 오염·라벨 상태까지 검증한 성능으로 보고하지 않는다.

## 2. 데이터 파일과 결과 보존

- 원본은 `data/raw/`, 가공 데이터는 `data/processed/`를 권장 위치로 사용한다. 원본을 수정하지 않는다.
- 원본·대용량 데이터·모델·가상환경·비밀키는 기본적으로 Git에 넣지 않는다. 재배포 가능한 작은 샘플과 작은 결과 요약은 출처·포함 이유를 기록한 뒤 넣을 수 있다.
- `.gitignore`는 첫 업로드 전에 실제 생성하고 확인한다. 이 문서는 Git 제외 설정 자체가 아니다. 이미 추적된 파일은 `.gitignore`를 추가해도 자동으로 추적 해제되지 않는다.
- Git에 없는 파일은 접근 권한을 갖춘 팀원이 같은 버전을 얻을 수 있도록 준비 절차를 문서화한다. 비공개 데이터는 경로·버전 안내만으로 복구 가능하다고 가정하지 않는다.
- 분할 ID·예측값·오류 사례도 개인을 식별할 수 있는지 확인한다. 식별 가능하거나 배포 제한이 있으면 Git 외부에 보관하고 승인된 팀원만 접근한다.

## 3. 실험 기록 형식

코드가 생기면 `reports/experiments/<run-id>/`를 실행별 기록 위치로 사용할 수 있다. 현재 실험 폴더나 기록 파일은 생성하지 않는다.

실행 ID 예: `2026-11-01-baseline-01` (형식 예시이며 실제 실행이 아님).

| 기록 | 필수 내용 |
| --- | --- |
| 식별·상태 | 실행 ID, 작성자, 실행 일시, 완료/실패/부분 실행/미실행 |
| 입력 | 데이터 버전/해시, 분할 버전 또는 ID 위치, 타깃·피처 |
| 재현 정보 | 코드 commit SHA, 미커밋 변경 유무와 보존 위치, Python·패키지·하드웨어, 실제 실행 명령 |
| 설정 | 전처리, 모델·하이퍼파라미터, seed, 탐색 범위 |
| 결과 | 평가셋, 표본 수, 지표 정의와 값, 실행 시간 |
| 해석 | 변경 이유, 비교 대상, 실패·한계, 결과·그림의 위치 |

최종 제출 결과는 커밋된 코드로 재현한다. 개발 중 미커밋 코드로 실행했다면 그 상태와 변경분을 기록해 다른 commit의 결과로 오인하지 않도록 한다.

선택한 설정을 고정한 뒤 train+validation으로 재학습할 경우, 최종 평가용 test는 계속 분리한다. 선택 당시 결과와 재학습 후 결과를 구분해 기록한다.

## 4. 공통 기준 변경 절차

1. 바꾸려는 항목과 이유, 영향을 받는 코드·노트북·결과를 정리한다.
2. 요청 범위 안에서 관련 구현과 이 문서를 함께 수정하고 PR에 변경 전후를 적는다. 다른 사람의 진행 중 작업에 영향을 주면 조율한다.
3. 데이터·타깃·분할·지표가 바뀌면 새 버전을 부여하고 필요한 비교 모델을 다시 평가한다. 이전 결과를 삭제하거나 서로 다른 조건의 점수를 같은 표에서 직접 비교하지 않는다.
4. 병합 후 결정 표를 최신 상태로 유지하고 실험 기록에 적용한 버전을 남긴다.

제안만 하는 경우에는 ‘제안’으로 적고 결정된 값과 구분한다. 제안된 주제와 실험 계획은 README를 따르며, 최종 데이터·세부 설정·역할은 확인 전까지 미정으로 둔다.
